# 工程决策、断连收据恢复与慢测试提速规范

在涉及重复计算、外部调用、长耗时等待、写文件、跑测试或重试的长程任务中，提前判断各环节如何相互影响：哪里适合直接用内置编辑工具读写，哪里需要脚本自动化，什么信号支持继续推进，什么迹象要求先查进程与收据状态。日常并行开发、Worktree 隔离、两轮止损与双轴审查主流程直接配合 `implement-spec` 技能执行。

---

## 一、信息对齐与软件设计（划分模块与状态账本时必读）

软件从头到尾处理的只有信息在**外部环境、内部模块、外部调用者**三者之间的传递与核对。每一次跨边界核对事实、规则或状态，系统都要交一笔信息对齐税：

$$\text{软件总信息对齐成本} = \text{核对信息的【频次】} \times \text{每次核对的【单次成本】}$$

优秀的软件架构只在三道边界上做五件事——两招砍**频次**，两招砍**单次成本**，一招守**大门口**：

| 所属边界与治理手段 | 主攻公式哪一项 | 工程判据（何时用这一招） | 核心做法与实测效果 |
| :--- | :--- | :--- | :--- |
| **1. 同频合并**<br>（内部模块间） | **猛砍【频次】**<br>消灭高频跑腿往返 | 同一道工序被拆成两半，上下游每走一步都要跨进程/跨房间传话对表 | 把步调一致的动作合进同一模块（如传数据+记账合成一步，收拢零碎外挂进程），大幅压缩往返轮次 |
| **2. 异频分离**<br>（内部模块间） | **猛砍【频次】**<br>消灭低频账本陪跑 | 快慢悬殊、毫无关联的几本账合住在一个状态文件里抢同一把锁 | 拆开快慢账本各管版本号（高频脉冲状态、任务元数据、单步结果三本账独立），彻底根除 `409` 并发冲突误杀 |
| **3. 通用石板抽离**<br>（内部模块间） | **猛砍【单次成本】**<br>消灭两两翻箱倒柜 | 多处模块都要反复查询同一份公共参考目录或重复解析同一份大文件 | 将公共规则或参考目录抽成门口的**只读石板**（内存缓存或增量尾读），杜绝重复全量扫描与内存爆仓 |
| **4. 深模块信息封装**<br>（模块对调用者） | **猛砍【单次成本】**<br>压缩双方共同知识 | 修改一处代码需核对别处十几条隐含规则，或内部动辄报错逼外部写善后代码 | **窄门进、深屋算、把错误定义出局**：复杂判定锁在模块内部；底层用幂等认账与内容指纹吞下冲突，对外 0 甩锅报错 |
| **5. 边界环境归一化**<br>（系统与容器入口） | **同时砍【频次×成本】**<br>防外部脏数据入室 | 外部环境输入格式千奇百怪或跨独立容器（如外部 AI / 浏览器宿主）状态不一 | 在系统/容器大门口做一次统一过滤与格式转正，免掉内部模块无休止的分类讨论 |

## 二、看见失败时，先分清已经发生了什么

| 眼前看见的信号 | 能支持的判断 | 下一步动作 |
| :--- | :--- | :--- |
| **明确的安全拒绝或授权范围拒绝** | 当前动作未获允许，并非普通代码逻辑错误 | 停止被拒动作，保留原因；在已授权范围内诊断或请用户拍板 |
| **参数缺失、语法错误、目标不唯一** | 调用或定位有具体笔误 | 直接修正参数或定位，不盲目扩大权限 |
| **文件内容或版本号与读取时不同** | 写入依据已过期 | 重新读取最新状态并合并，不强行覆盖新修改 |
| **远程/工具调用超时、断开或无返回**（如网页端/网关 60～120s 断流） | 本地进程可能仍在运行或已结束 | **先查后台任务状态、本机进程与证据目录收据（`run.json` / `pipeline.state.json`），严禁立即重复提交同一命令** |
| **命令退出码为 0，结果却不符合目标** | 进程走完不等于业务目标达成 | 读取实际输出文件核对内容，修正逻辑或用例 |

## 三、超时之前，就要安排怎样识别和恢复任务（防重复踩踏）

1. **单次连接等待可能短于本地完整耗时**：启动耗时超过单次网关等待窗口（60～120s）的任务时，优先使用非阻塞后台会话（如 `exec_command` + `session_observe`）或带持久化收据（`run.json` / `pipeline.state.json` / `terminal.json`）的入口。
2. **断流后先查现场，复用已完成收据**：通信中断后先检查本机进程与证据目录：
   - 若进程仍在运行，则改用短间隔继续观察收据直至结束；
   - 若已生成同候选版本的完整终态收据，则直接读取复用；
   - **仅在确认原任务未运行且无有效结果时才重新发起**。
3. **单实例独占锁防重**：长耗时批量与测试入口内置操作系统级单实例锁，自动拦截超时重发或并发误触。

## 四、慢测试提速工具箱（仅在 `setup > 1s` 或全量长尾时按需启用）

普通快速测试保持原生临时目录夹具（如 `tmp_path`）即可；当单题准备耗时 `setup > 1s` 或全量批次过慢时，选用以下**零冲突提速手段**：

| 提速手段 | 什么时候用？ | 怎么做到和现有工具 0 冲突？ |
| :--- | :--- | :--- |
| **1. 多进程按耗时排队并发**<br>（4 进程并行） | 跑集成分支末尾 1 次全量或大模块回归测试时默认开启 | 按历史真实耗时**从长到短排队**（最慢的测试模块最先开跑，避免小文件假记录误导排期），分发给 4 个独立工作进程并行跑，不动任何测试源码。 |
| **2. 只读母版 + 秒拷小桌面**<br>（`copytree` / `newContext`） | **仅当**同一批测试反复执行一模一样的重型初始化（如建库+灌入大体积合成样例 `> 1s`）时 | 在同进程/同模块内建 1 份只读母版，各题 `copytree` 秒拷副本目录（浏览器测试复用同进程 `browser` 母体并每题新建 `browser.newContext()`）；要求特殊空库或怪状态的测试继续用各自原生夹具，互不干扰。 |
| **3. 超慢大文件外部点名册分包**<br>（`manifest.json`） | 单个测试文件耗时 `> 60s` 拖慢整批尾巴时 | **不物理切割测试源码文件**，只在运行器的 `manifest` 清单里把该文件的测试条目（`nodeids`）分成 2～3 组（同函数的参数化子项绑在同一组）并发执行。 |
