# 协同实施规格与工单图

你已经拿到一份规格。规格应关联描述如何实施它的工单。

应当已经为你提供工单跟踪器。若没有，请让用户运行 `/setup-matt-pocock-skills`。

目标是在单一**集成分支**完成整份规格，并按照工单跟踪器的流程解决每一张工单。

工单通过阻塞依赖形成**任务图**，决定哪些工单位于能够开始实施的**可推进前沿**。

- 当**可推进前沿**只有一张局部工单（或单次直接开发需求、或多张必须串行修改同一批文件的工单）时，可以直接在当前工作树运行 `implement`。但是，如果直接实施出现**同因两次停手**（`Status: Two-Strike-Stop`）（或工单属于跨模块清理/收缩），应先把被证伪的方法记入工单的 `Attempt Log`（`AttemptLog`），然后最多委派一次给全新子代理。如果仍被阻塞，则将工单标记为**隔离待解**（`Status: Quarantined`），继续推进其他未被阻塞的工单，不得停止主会话。
- 当任务是在至少 20 个相互独立的文件上执行同质扫描或机械式变换时，直接运行本地脚本（`max_workers=4`，把进度写入 `run.json` / `pipeline.state.json`）；仅为脚本标记的异常派发子代理。

与子代理之间应尽量减少通信。主要通过**上下文触发指针**指向规格、工单、研究笔记和先前提交，不重复指针已经可达的内容。

**实施子代理**应尽可能在后台并发运行。通过宿主原生编排派发：网页端使用宿主默认设置（不传模型或推理强度参数）；本地 CLI/IDE 宿主选择匹配的自定义代理角色（`explorer`、`implementer`、`implementer_deep`、`reviewer`），由宿主配置决定模型和推理强度。

## 步骤

1. 读取规格和工单，理解整个任务图。

2. （可选）派遣**探索子代理**（`explorer`），调查工单实施所需的代码库文件或外部资料。确保该代理能够把 Markdown 调查笔记保存到仓库外、后续子代理都可访问的目录，避免实施子代理重复调查。

3. 创建集成分支。先在集成分支直接落地少量共享**接口契约**或预先重构的阻塞项，使并发工单都以已经锁定的**可替换接缝**为分支起点。如果工单跟踪器通过 PR 关闭工作，或用户要求 PR，则在第 5 步首次合并之后新建草稿 PR（没有领先于主线的提交时无法创建），并将其标注为关闭规格和工单。

4. 为各工单使用**实施子代理**（局部切片用 `implementer`，跨模块状态或生命周期工单用 `implementer_deep`），每个代理使用独立工作树和独立分支。每个实施子代理必须：
   - 在开始前确认自己的工作树基于集成分支；若不是，先重置到集成分支。
   - 将模块解析路径（如 `PYTHONPATH`）绑定到自己的工作树根目录，并在**紧反馈回路**中仅运行正在编辑的单个测试文件。
   - 调用 Skill 工具执行 `tdd`，构建工单要求的行为。
   - 追踪该工单的**变更波及面**（被改动**接口契约**的所有调用方与导入方），运行覆盖这些调用位置的测试文件，直至全部通过。
   - 对保留面向用户的行为与既有验收判据的不破坏性内部调整或波及面适配，在规格/工单跟踪记录的 `## Accepted Amendments & Internal Adaptations` 下登记。若冲突要求改变面向用户的行为或既有验收断言，则在交互时询问用户；无人值守时返回 `Status: Quarantined` 及冲突详情。
   - 暂存所有修改和新文件（`git add -A`），在工单分支提交候选快照（`git commit`），针对 `<integration-base>...HEAD` 调用 `code-review`，按照**生效规格**（`Original Spec ⊕ Accepted Amendments`，即原始规格 ⊕ **已接受修订**）检查；修复问题并更新分支提交，直到审查和测试都通过。
   - 如果连续两次处理同一根因却没有进展（失败测试数量不下降；不计入 `60s` 传输/超时断线，后者必须先检查 `run.json` 回执），则执行**同因两次停手**：将失败编辑回退到最近一次测试通过的提交，在工单的 `## Attempt Log & Quarantine Status` 下追加三行记录（`[1] approach tried`、`[2] falsifying error/evidence`、`[3] dead-end constraint for successor`），并返回四行交接（`Status: Two-Strike-Stop`、`Pointers`〔含 `Attempt Log` / `AttemptLog`〕、`Verified`、`ResidualRisk`）。
   - 汇入集成分支最新提交到自己的分支后，返回四行交接（`Status: Done`、`Pointers`、`Verified`、`ResidualRisk`）。

5. **分层故障处理、限次接力与隔离待解后继续推进**：
   - 当子代理返回 `Status: Two-Strike-Stop` 时，检查该工单此前是否已经接力一次：
     - **首次停手（$N_{\text{relay}} < 1$）**：立即创建**一个**全新、能力升级的子代理（本地 CLI/IDE 使用 `implementer_deep`；网页端使用新的原生子代理），传入四行交接指针与工单 `Attempt Log`，让它以干净上下文接管，避免重试已经被证伪的方法。
     - **接力额度耗尽（$N_{\text{relay}} = 1$），或 `Status: Quarantined`（规格冲突或缺少外部凭证）**：将工单标记为 `Status: Quarantined`，仅阻塞它直接及传递依赖的下游工单。**主会话不得因此停止整个有向无环任务图的实施**：立即绕过已隔离子图，继续派发和完成其余位于**可推进前沿**的未阻塞工单。
   - 实施子代理完成并返回 `Status: Done` 后，通过**合并子代理**（`implementer`）将审查通过的分支合入集成分支（`git merge --squash` 或无冲突普通合并）。

6. 若合并改变了**可推进前沿**，继续派发实施子代理处理新解锁、未被阻塞的工单，以尽可能提高并发度；持续推进，直到没有可执行的未阻塞工单。

7. 所有未被阻塞的工单完成后，在集成分支上**只运行一次**完整测试套件（单实例批次；如果长批次断线，先检查 `run.json` 进度回执再决定是否重跑）。如遇跨工单集成问题，运行最终集成 `code-review`，交由实施子代理修复。

8. 如果存在草稿 PR 且所有工单均已完成，则将 PR 标为可审查。按照工单跟踪器的流程解决已完成的工单，按合成自动化测试、真实外部 API、真实机器 UI 三个层次报告验收，并明确标记未执行的层次。同时报告集成分支和所有 `Status: Quarantined` 工单，附其 `Attempt Log` 以及需要用户做出的准确决策。

9. 清理所有实施子代理的工作树。
