# 按规格与工单实施

在**当前分支**上直接实施用户规格或工单所描述的工作。

如果用户传入工单引用，先从工单跟踪器获取工单，并在开始前说明其标题。引用有歧义时询问用户。

在事先约定的**可替换接缝**上，尽可能调用 Skill 工具执行 `tdd`。

实施期间，在**紧反馈回路**中持续运行类型检查和当前正在修改的单个测试文件。

实现转绿后，追踪**变更波及面**：搜索代码库中所有触及已修改**接口契约**的调用方、导入方、路由和共享状态，并运行覆盖这些调用位置的每个测试文件，直到全部通过。只有用户明确要求收尾验收时，才运行完整测试套件。

如果实施过程中需要不破坏既有行为的内部调整（例如提取辅助函数，或修改处于**变更波及面**内的调用方签名），且这些调整保留面向用户的行为和既有验收判据，则在规格/工单跟踪记录的 `## Accepted Amendments & Internal Adaptations` 下追加简短说明。若冲突要求改变面向用户的行为或既有验收断言，则在交互场景下询问用户；无人值守时将工单标记为**隔离待解**（`Status: Quarantined`），记录冲突，不得擅自改写规格或削弱测试。

暂存所有已修改和新建文件（`git add -A`），并在当前分支提交候选快照（`git commit`），使 `HEAD` 捕获完整的进行中工作树，并提供干净的回滚锚点。

调用 Skill 工具执行 `code-review`，审查范围为 `<base>...HEAD`，按「**生效规格** = 原始规格 ⊕ **已接受修订**（`Original Spec ⊕ Accepted Amendments`）」评估。修复发现的问题，重新运行受影响的测试文件，更新分支提交，直到审查与测试均通过。

按三个层次报告验收结果：合成自动化测试（列出已运行的**变更波及面**测试文件）、真实外部 API、真实机器 UI。未执行的层次必须明确标记。
